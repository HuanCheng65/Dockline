# 实时状态（Live Status）功能设计

状态：讨论定稿 2026-08-24；2026-08-26 按已落地的实现修订。Claude Code 这一路已可日用（含就地授权），媒体已接通并上过屏（取色、面板版面、进度条与均衡器都按实机观感改过，见 §5.2、§5.3、§5.5）。全局区降级为待定，见 §7。第 9 节两项只有设计，没有实现。
适用范围：Dock 替代项目的实时状态子系统。基础设计（底部窗口条、每窗口一个 slot、v3.1 定稿）见项目主计划文档。

## 1. 定位

这个功能的本职是注意力路由：后台任务干活时把你隔离出去，需要你的那一刻把你精确拉回来。进度展示、播放信息等属于附带能力，设计冲突时以注意力路由优先。

有价值的场景：

1. AI agent 会话（Claude Code 等）—— 专用模块，价值最高
2. 终端长命令（编译、测试、rsync）—— 通用观测
3. 媒体播放 —— 专用模块
4. 实验/训练监控 —— 走通用上报协议，脚本自己 curl
5. 下载/文件拷贝 —— NSProgress + FSEvents，后置

**第一版做 1 与 3。** 取的不是价值排序，是设计覆盖面：agent 压的是等待态与一次性事件，媒体压的是常驻文本与点缀层，两个模块正好把下一节那两层各撑开一半。终端长命令与 agent 是同一个形状（在跑 → 完成 / 失败），进第一版只增加工作量，不增加要验证的东西，因此后置。已知代价：媒体是第一版里唯一一块新基础设施（见第 5 节的跳板方案），大概率也是先出问题的那个。

**状态来源按种类分两类，不按复杂度分。** 这条是后来改的，原先按复杂度切（简单任务走通用协议、vibe coding 写专用模块），而复杂度切出来的两边恰恰要在渲染层汇合，等于把差别推到了它最不该在的地方。按种类切，差别落在它本来就在的位置：

- **任务型**：有生命周期（在跑 → 等你 → 停了），因而**可以**要你的注意力。agent 会话是这一类。
- **常驻型**：没有生命周期，不会结束，也**永远不该**要你的注意力。它存在是为了一眼看得到、顺手控制得了。播放是这一类。

这条界线直接解释了一件事：**播放不能做成第四档显著度**。第 3 节那三档整个建立在「此刻谁在等谁」上，而播放对这个问题的回答是「没人在等谁」。塞进去等于让一件不参与注意力竞争的事排进注意力队列，而注意力路由正是这条产品线的本职。

两类**只在格子那一层汇合**（两行字、图标、点缀），面板各写各的：一条时间线和一个播放器没有一处能共用，硬套一个模板只会得到两边都不称职的一张卡。代码里那道缝就是 `CellStatus`。

## 2. 宪法：slot 分层模型

这是整个功能的最高规则，后续所有状态源接入都用它裁决，不逐 case 讨论。

一个 slot 分两层：

**身份层 —— 任何状态源不得改写。** 包含三样：

- 位置：slot 在条上的位置永远不因状态变化移动
- 图标：App 图标永远不被替换（角标、点缀可以叠加，见下）
- 点击语义：左键点击永远是召回窗口，全条统一，无特例

身份层服务肌肉记忆和视觉搜索，价值来自稳定。图标换成专辑封面、slot 变成内嵌播放器，均属违宪。**封面以角标形式挂在图标一角不违宪**：图标本身没有动，你按肌肉记忆找的那个东西还在原处。

**状态层 —— 状态源可以改写。** 包含两部分：

- 文本层：slot 的文字标签，**两行**。有会话时第一行是这条会话的名字，第二行是此刻的状况；没有会话时保持原样，也就是歧义驱动的窗口标题。

  **会话名按可靠程度依次退让**：Claude Code 自己维护的会话标题 → 本轮提示词摘要 → cwd 目录名 → 歧义驱动的窗口标题。会话标题不在任何 hook 事件的输入里，但每个事件都带 `transcript_path`，标题在那份文件的 `ai-title` 记录里，取最后一条。transcript 会长到上百 MB（本机实测 117MB），因此从文件尾部倒着按块回扫、回扫有上限，实测 0.3ms，便宜到每个事件都重算一次，标题跟着对话走。

  第二行在跑时是**当前动作**（读取 / 编辑 / 执行 + 作用对象），等待时是四档之一，停了是「✓ 已完成」。

  **宽度：有会话的格子文本区固定取上限。** 两头都试过不行——让第二行参与定宽，格子会跟着模型的每一步呼吸，右边整排跟着晃；只按第一行定宽，任务名一短（窗口标题退化成一个词时尤其如此），第二行就被挤到只剩一个词加省略号。取上限则宽度只在会话上格子与会话结束时各变一次。

  **这是对身份层那条「位置永远不因状态变化移动」的一处明确让步。** 让步的理由是：条本来就会因标题变化改宽度（`labelWidthStep` 那 6pt 迟滞正是为它存在的，一个 App 开出第二扇窗口时格子也是当场长出标题区），而不让步换来的是一格读不出任何东西——那正是这条产品线要解决的问题本身。

  两行都要**先截断再交给视图**：`Text` 只会折行，第一行折下去就把第二行挤没了。
- 点缀层：叠加在图标上或图标旁的小元素——状态点、进度环、均衡器、角标。

  **图标的角是有数的**：右上未读角标、左上标签页数、右下封面加均衡器，还剩左下一个。运行点与状态环不在这份账里——点落在图标**下沿之外**那条带里（`dotDrop`），环画在格子边缘上，两者都不占角。

  这份账曾经写成「四个角已经占满」，据此否掉了封面角标（见 §5.2）。那是**数错了**：把落在图标外面的运行点算成了一个角。教训不在算术上——一条凭空多出来的限制，反过来把一个本来成立的设计砍掉了，而且它此后一直以「已论证过的约束」的身份被引用。**点缀层确实有容量上限，但上限是几个角就是几个角，不是随手报出来的一个数。**

## 3. 显著度分级：谁在等谁

显示强度由「此刻谁在等谁」决定，三档：

**它在干活，你不用管（working）**
唯一需要传达的是「还活着」。静息态只给低调呼吸动效点，不给文字——文字诱导阅读，阅读即打断。当前动作细节全部收进 hover。

**它在等你（waiting）**
唯一允许高显著度的状态。格子第二行一个词说明等什么——**待回答 / 待授权 / 待审阅 / 待输入**，四档同一句式起头：它们是并列的等待，差别只在等什么，句式一致才读得快。格子边缘常亮（不呼吸：那会与它要表达的紧迫感互相稀释），面板里的图标按四档各给各的（锁 / 问号 / 计划 / 键盘），那一眼要读出「在等什么」而不只是「在等」。

**它停了（done / failed / quota）**
一次性事件，走「未读」语义：✓ / ✗ 加一句摘要，**停留到用户点击那一格为止**。被限额是独立状态（含义与完成相反）。

**前台那一格不画终态的彩色边框。** 前台格子本来就带着亮底与自己的一圈描边，终态再叠一圈颜色上去，两条边挤在同一个圆角上，读起来是一格画了两遍。退掉的只是这一圈颜色，终态本身不受影响。

**同一格上撞了好几条上报时谁露面**：等待 > 终态 > 在跑；同档里**等待按先来后到**（等得最久的那条最该先被理会），**在跑与终态按最近更新**。同档一律先来后到的话，一条陈旧的会话会把同一格上一条正在活动的会话永久遮住，而它自己再也不会更新（实测撞到过）。

进度的口径定死为两半，免得后面每接一个状态源重问一次：**有确定进度时，格子边缘走进度环**——它属于点缀层，显著度本来就低，不构成打断，也是主计划文档 §3 的既定表达；**文字型进度（任务 3/7、耗时、ETA）只在 hover 中出现**，永远不主动争取注意力。

**已废弃：胶囊。** 原方案是等待与终态从格子上方浮出一个胶囊（向上浮出而非条内横向扩展，因为横向扩展会推挤邻格）。做出来之后废掉，两条理由：格子学会说话之后，胶囊只是把同一个词放大重复了一遍；而它占的正是浮层的位置，会盖住同时展开的预览卡（实测截图）。它想要的那个「响到能把人拉回来」的表面，由能就地作答的面板来接（见 4.4）。

决策放在哪做，由决策大小决定：

- 小决策（选项式）就地在面板里完成：展示完整命令的允许 / 拒绝
- 大决策（需要读代码、读完整计划）面板只提供一键跳转到对应窗口，不塞进小卡片

## 4. Vibe coding 模块（Claude Code）

### 4.1 数据链路

Claude Code hooks 支持五种 handler 类型（`command` / `http` / `mcp_tool` / `prompt` / `agent`），其中 `http` 让 hook 直接把事件 JSON POST 到本地 URL。hooks 在终端、IDE 插件、桌面 App 中触发相同事件。

**但不能全走 http。** hook 的公共字段里没有进程号（逐字核对过：`session_id`、`prompt_id`、`transcript_path`、`cwd`、`permission_mode`、`effort`、`hook_event_name`）。http handler 又没有子进程，于是两件事同时落空：拿不到进程树就**不知道宿主 App 是谁**，拿不到 pid 就**没有存活信号**——而 `SessionEnd` 只在正常终止时发，agent 崩掉时什么都不发。

原定按频次分工：低频且与绑定有关的走 `command`，高频的走 `http`，为的是省掉每个事件一次进程启动。

**第一版全部走 `command`。** 那笔要省的开销实测是 **8.0ms**（本机 20 次取平均，含进程启动与发通知），挂在最高频的 `PostToolUse` 上也远小于一次工具调用本身，为它加一整套本地 HTTP 服务不划算。全走 `command` 另有一处好处：每个事件都带着进程树，宿主 App 与存活信号任何时候都拿得到。

**但 `http` 迟早要做，理由不是这 8ms，是它能跨机器。** 见 4.5：远程会话没有别的路可走。届时上面那条「不能全走 http」的约束依然成立，本地这条链路不跟着换。

登记的事件与它们表达的状态：

| 事件 | matcher | 状态 |
|---|---|---|
| UserPromptSubmit | — | working |
| PostToolUse | — | working。它同时负责把等待态撤下：授权批下来、问题答完之后，紧接着就是一次工具调用 |
| PreToolUse | `ExitPlanMode\|AskUserQuestion` | waiting(plan / question) |
| Notification | — | waiting，具体看 `notification_type` |
| Stop | — | finished(done)，摘要取回复首行 |
| StopFailure | — | finished(failed)，取 `error_type` |
| SessionEnd | — | 撤下 |

**`PermissionRequest` 起初不挂，后来挂了。** 起初的理由是：那是个决策事件，hook 的返回值能左右这次授权准不准，而这里是个报状态的东西，不该有影响授权结果的机会，哪怕只是因为写错了。推翻它的是**失败的形状**：这条路上的每一种坏法——条没在跑、连接断了、进程被超时杀掉——都表现为**不打印决定**，而不打印决定正是 Claude Code 本来就用来「该问用户了」的信号。只有特意打印出来的那一个决定才算数，所以写错的后果是拿不到这条捷径，而不是放行了什么。就地授权因此成立，见 §4.7。

`Notification` 的 `permission_prompt` 仍然接着，它管的是另一半：授权请求走完 §4.7 那条路却没人应答时（条没在跑），这条通知照旧把格子翻成「待授权」。

`Notification` 不加 matcher。它的取值另有一套（`notification_type`），matcher 写错的后果是 hook 永远不触发，而这种失败是哑的；放到适配那一侧去判，至少看得见。

会话消失有两个来源，都要接：正常终止走 `SessionEnd`，异常消失靠盯 hook 报上来的宿主 pid。不设超时——「多久算没动静」只有上报方知道，替它猜只会让长任务的指示器中途消失。

安装走 `dockctl install-hooks`，写用户级 `~/.claude/settings.json`，`uninstall-hooks` 撤销。三条自我约束，因为那是别人的全局配置：解析不了就原样不动并报错（配置里若有注释一类的非标准写法，覆盖写回等于替用户重写他的配置）；写前留一份带时间戳的备份；重复安装先摘掉自己上次留下的条目，撤销走同一段。已知代价是写回时整个文件按标准 JSON 重排缩进与键序。

### 4.2 事件映射

| 事件 | 用途 |
|---|---|
| SessionStart / SessionEnd | 会话状态的创建与移除 |
| UserPromptSubmit | 进入 working，**并且标记新的一轮**（见 4.5）。用户那句话在 `prompt` 字段里，不是 `user_input` |
| PreToolUse / PostToolUse | 更新当前动作。`PreToolUse` 收全部工具、并取 `tool_input`：动作的对象与量化结果都在里面。`PostToolUse` 不带工具，表示模型在生成下一步 |
| PermissionRequest | 就地授权（§4.7）。**阻塞**，打印出决定才放行或挡下 |
| Notification（matcher: permission_prompt / idle_prompt / agent_needs_input / agent_completed） | 各类等待信号 |
| AskUserQuestion（经 PreToolUse 拦截） | 选项式提问。**只能报状态，答不了**，见 §8 |
| ExitPlanMode（**它是工具名不是事件名**，同样经 PreToolUse 拦截） | 计划审阅，跳转窗口处理 |
| TaskCreated / TaskCompleted | 任务清单进度（n/m） |
| SubagentStart / SubagentStop | 并行子 agent 数量 |
| Stop | 完成，last_assistant_message 字段截一句做摘要 |
| StopFailure | 轮次因 API 错误结束，带 `error_type` / `error_message`——失败与限额靠它区分 |
| PermissionDenied | auto 模式自动拒绝的记录：本该问你、被规则挡掉了 |
| Elicitation / ElicitationResult | MCP 向用户要输入，同属「在等你」 |
| CwdChanged（带 `new_cwd`） | 会话换了工作目录，直接喂给 4.3 的窗口匹配 |
| TeammateIdle | 又一路空闲 / 等待信号 |
| Notification（matcher: quota_auto_resume_fired / _stale / _disabled） | 限额相关，供第 7 节的全局区 |

**过线的是归一化的动词，不是工具名。** 起初送的是 Claude Code 的工具原名（`Read`、`Bash`），条那边拿它当本地化的键——那等于把一个上报方的工具表焊进了界面文案：再接一个 agent，同一件「读文件」就要在资源里躺两份键，而资源会随上报方的数量增长。现在 `dockctl` 这边定一套共用词汇（read / edit / write / run / search / fetch / websearch / subtask / todo），每个适配器把自己那份工具表翻过来，条只认这几个词。

**认不出的工具原样送它的名字**，不归一成「其他」一类的说法：条那边找不到对应文案就直接显示这个名字。泛化的说法把「这一步在干什么」这个唯一要答的问题答成了废话，而工具原名至少是真的。

事件输入自带 permission_mode 字段，可判断会话是否 auto 模式。auto 模式下逐条批准基本消失，「需要你」的时刻集中在：agent 提问、计划审阅、未被规则覆盖的权限、完成、限额。设计以这几类为主，逐条批准为辅。

transcript JSONL（hook 提供路径）做 tail 补充细节：当前文件、命令、耗时。**但它是异步写的，会落后于内存里的对话**，当前轮的最后一句话要用 `Stop` / `SubagentStop` 自带的 `last_assistant_message`，不要去 transcript 里捞。

### 4.3 会话 → 窗口映射

会话键直接用 hook 自带的 `session_id`，不必另造——它在每个事件里都有。要解的只剩「这个会话住在哪扇窗口」。

- 独立终端（Ghostty、iTerm 等）：进程树直接爬到窗口
- VS Code：pty host 是共享进程，**爬得到 App、爬不到窗口**。实测链路 `zsh ← claude ← fish ← Code Helper ← Code`；Code Helper 虽有自己的 bundle ID 且是 LSUIElement，但未在 `NSRunningApplication` 注册，不会把上报误停在它身上。主路是用 `cwd` 末段匹配窗口 AXTitle——VS Code 默认标题的尾段就是工作区文件夹名，而 `cwd` 每个事件都带，`CwdChanged` 负责保鲜
- **前台焦点只当同分候选之间的裁判，不许翻案。** 仅当 cwd 匹配出多个候选时才用它，且焦点窗口必须是候选之一，否则忽略。理由是失败的形状不同：cwd 匹配失败是**歧义**，当场就知道有几个候选对得上，可以拒绝绑定；而「取上报那一刻的前台焦点窗口」失败是**静默绑错且无界**，可能绑到另一个 App 的窗口上。它还恰好踩在这个功能存在的理由上——你提交完就切走，hook 到达时读到的焦点已经是你切过去的那扇
- 匹配不上、或候选里没有焦点：不绑，退回 App 级（即现在的行为），并给一个一次性认领的入口
- 认领**暂不跨重启持久化**。那需要一个跨重启稳定的窗口身份，是主计划文档里单列的 spike；第一版的绑定只在会话内，重启后下一次提交 prompt 即重新绑上
- 同窗口多 session：slot 显示最高优先级状态（waiting > working），hover 展开列出全部

### 4.4 面板

悬停一格就是这条会话的面板。它不是另一张卡：**有会话时缩略图不画**（那扇窗口长什么样此刻不是问题，而一张小图浮在卡片中央、两边留白，比不画难看得多），但按住空格要大预览时照旧铺满、会话区跟在下面——那一刻用户是明确要看窗口的。缩略图区按内容多少让位，同一棵视图树、同一个 `.frame`，不分成两张卡。

```
│ ●  生成中                               │  当前那一行
└────────────────────────────────────────┘
```

几条定死的规矩：

- **对齐先于修辞。** 图标一栏、动作名一栏都定宽，几行的动作名从同一个横坐标起头。这是它读起来像一份记录而不是几句碰巧开头相似的话的全部原因。动作名与对象因此在模型里**分开存，不拼成一句**——拼好了就再也拆不开。
- **对象走等宽字。** 文件名与命令是代码，正文字体里 `l` 和 `1` 分不开；换一种字本身也把两栏拉开层次，不必再画一条竖线。
- **当前那一行给完整的那一份**（命令全文），历史行给缩写：全文正是此刻要判断的东西。正在生成时它没有对象——那时把上一步残留的命令摆在这里，等于说它还在跑那条命令。
- **在跑时最后一步就是当前那一行**，历史里不再列一遍，否则是两条一模一样的记录。
- **只列末尾几条，所以要报出总数。** 没有总数的话，四行读起来就是「它一共就走了这几步」。
- **停了就贴结论，不再列经过。** 那一刻要的是结果；经过想看的时候还在终端里。回复按**行内 Markdown** 渲染：`.full` 那一档认得块结构却把字符流里的换行全吃掉，直接渲染会连成一行（实测）；行内这一档保留换行，粗体、斜体、行内代码都在，行内代码要自己换成等宽字。
- **本轮用时，不是会话总时长**，且**停了就停表**。会话可以开着一整天，那个数字不回答任何问题；而已经结束的任务，数字再往上走说的就不是它跑了多久了。数字走等宽，不然每跳一秒右边那一栏就横着挪一下。
- **有东西等着你批时，这份记录整个让位。** 面板换成 §4.7 那一档：要做什么、做在什么上、批不批。那一刻卡片的用途不是让你读进度，是让你按下去。
- **动效不许用来争夺注意力；表达一个你自己开启的持续状态可以。** 这一条改过：原文是「条上会动的只有格子边缘那一处，再加第二样就破了」，那条一度被拿来否掉播放的均衡器。但它针对的其实是**抢注意力的动效**——会话那圈呼吸的边框是在喊「看我」，所以它要独一份。均衡器不是：那是用户自己放的歌，他知道它在那儿，而且它小、恒定、不闪不长大。按原文一刀切，等于让一条为 A 写的规矩去裁 B。计时照旧只在面板存在的那几秒里跑。
- **卡片的高度必须用画它的那套引擎去量。** `NSString.boundingRect` 与 `Text` 的行高对不上（同一段实测 78 对 84，每行差 1pt），而卡片尺寸是浮层驱动、必须提前算准的，差一点就是底下空一条玻璃或者把最后一行裁掉。做法是把文字放进 SwiftUI 布局一次、读回 `fittingSize`，并且量的是**要渲染的那一份**（行内代码是等宽字，折行位置与纯文本不同）。

### 4.5 一轮

**用户提交提示词就是新的一轮。** 上一轮走过的步子、上一轮的结论都在那一刻退场——新提示词底下挂着上一轮的工具调用，读起来就像它正在做那件事（实测撞到过）。本轮用时也从这一刻起算。

**中断生成没有任何事件。** 文档原话：`Stop` hooks「don't fire on user interrupts」。所以按 Esc 打断之后，格子会一直显示「生成中」，直到下一次提交提示词（新一轮，立刻清掉），或者 `idle_prompt` 那个通知晚一点到、把它翻成「待输入」。**不设超时去猜**——那正是投机的兜底。`MessageDisplay` 事件也许接得到中断时终端打出的那一行，未验证。

### 4.6 远程会话（单列，第一版不做）

SSH 到另一台机器上跑 Claude Code——VS Code Remote 的集成终端即属此类，那里的 agent 进程整个在远端。本地这条链路对它三处同时失效，三处彼此独立：

1. **传输。** `dockctl` 发的是分布式通知，那是本机同一登录会话内的 IPC 总线，不跨机器。
2. **宿主解析。** 远端的祖先进程是 sshd / vscode-server，且那是 Linux，`NSRunningApplication` 不存在，dockctl 本身也编不出来；即便爬得到，远端 pid 在本机没有意义。
3. **标题匹配。** VS Code Remote 的窗口标题多一截远端标签（实测：`欢迎 — quiver [SSH: RUC_dev]`），切段之后是 `quiver [SSH: RUC_dev]`，与目录名 `quiver` 不相等。

**出路是 `http` handler，它跨得了机器，而分布式通知跨不了。** 顺带解掉第 2 条：hook 自己发 POST，远端不需要装任何二进制。形态是本机监听 `127.0.0.1`，端口反向转发进远端，远端的 hook 指向 `http://localhost:<端口>`，URL 或请求头里带上自己的主机名与安装时生成的令牌。

第 3 条反而在远程更好办：标题里的 `[SSH: RUC_dev]` 直接给出是哪台机器，目录名再在同一台的多扇窗口之间区分，两个独立信号。匹配规则要加一条**指名 VS Code Remote 标题格式**的特例——段等于目录名（本地），或段以「目录名 + 空格 + `[`」开头（远程）。写成特例而不是把匹配放宽成模糊包含：放宽会把本地那一侧的误匹配一并放进来。

三处已知代价：隧道断了就静默失效，而 hook 连不上会在**每一个事件**上报错，很吵，失败怎么表达要另想；那个端口是个入口，远端任何进程都能往里发，内容只影响条上画什么，风险低但仍需令牌；不同远端机器上的同名目录会撞，失败形状与本地一致（歧义即拒绝绑定），这条不必额外处理。

单列的理由是它要新增本机 HTTP 监听、一套令牌、一份远端安装流程，三样都不小；而本地这条链路刚验通，不该在它还没跑够日常使用的时候就往上叠。

### 4.7 就地授权

条上说得出「待授权」还不够——批准仍然要切回编辑器，而「尽可能不用打开 VS Code」正是这条线存在的理由。`PermissionRequest` 是**阻塞**的：它停在那里等 hook 打印决定，期间 Claude Code 停在这一步不动。这一档因此归条所有。

**文档与实现对不上，以实测为准。** 官方文档写的 `decision` 是一个字符串，取值 allow / deny / escalate；本机 2.1.245 实际认的是一个**对象**：

```json
{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}
```

拒绝是 `{"behavior":"deny","message":"…"}`，`message` 会进模型的上下文。**没有 escalate 这一档**：什么都不打印就是交回 Claude Code 自己那套流程。这一条读的是二进制里那段解析代码，然后照两种形状各跑了一遍验证的——文档那一种被完全忽略。

其余实测读数：

- **只在真会弹对话框的时候才触发。** 规则已经批准的、`auto` 模式下自动放行的，这个事件根本不发。`-p` 无头模式下权限请求直接被拒，也不发——所以那个模式测不了这条路，必须开交互会话（本次用 pty 驱动）。
- **事件次序是** `PreToolUse` → `PermissionRequest` → 阻塞 → 决定。阻塞期间终端里**不弹**它自己的对话框。
- **`Notification` 的 `permission_prompt` 不等这个 hook**，它走自己的计时器，实测约六秒后照发。因此待授权这条记录不能挂在上报那条链上——那条通知一到就会把它冲掉。它单独存放，只在渲染时挂到对应那一格上。
- **载荷里没有 `tool_use_id`**（`PreToolUse` 有，这个事件没有，它多的是 `permission_suggestions`）。所以请求认不了 tool use，只能靠连接本身来认。

**通道是 Unix 域套接字，一次授权就是一条连接。** 状态上报是单向的、发完就走，分布式通知正合适；授权是一问一答，形状不同。选连接是因为它一并解掉了三件事：连不上 = 条没在跑；读到 EOF = 条中途退出了；这个进程被杀（hook 超时、用户中断会话）连接随之断开，条据此撤下这条待授权——两端都不需要发一条「我走了」。答复走同一条连接回去，所以答复串到别的请求上在结构上就不可能。

**不设我们自己的超时。** 这里等的是用户，「多久算不管了」不是我们能定的。外面那道界限由 Claude Code 自己给：command 型 hook 默认 600 秒，到点丢掉本条输出、照常弹它自己的对话框，什么都没丢。

**面板上只放这一件事。** 近期动作那几行让位——那一刻卡片的用途不是让你读进度，是让你按下去。版面只有三样：要做什么、做在什么上、批不批。要判断的那几行**不折行**：折了行的 diff 比截断更难读，而且定高的行让这一段成了算出来的而不是量出来的（量文字这条路在这张卡上已经错过两次）。截短了要说出截掉多少——一份被悄悄截短的 diff 会让人以为改动就这么点。

**替换只列真正动了的行。** 逐行求最长公共子序列。只掐掉两头相同的行是不够的：一次替换常常夹着没动的行，那些行会被同时列成删和增，等于在说「这一行动过」，而它没动。相同的行也不作上下文列出——面板只放得下十几行，摆没动的行会把改了的挤出去。行数超过上限（400）就退回只掐两头：最长公共子序列是二次的，而那么大的改动本来就该切回终端看。

**预览卡因此破了一次例。** 它向来只是「看一眼」，指针一离开那一格就收，整档不收事件。有待授权时这一档要点得着，且要撑住指针从格子挪到卡片的那段路（与浮层同一个宽限值）。答完就没东西可按了，照旧立刻收。

**同为等待时，待授权排在最前。** 它是唯一能在条上当场办掉的一档，其余等待只是在陈述。一律先来后到的话，一条更早的通知会把它盖住，用户没有地方按，而对面还阻塞着。

**提问与计划审阅不走这条路。** 它们也会触发这个事件，但批不下来：Claude Code 对「需要用户亲自交互」的工具只认带着答案的放行，光说一句「允许」会被忽略、照旧弹自己的界面（实测确认）。在条上摆一个按下去没反应的按钮比不摆更糟，所以那两档照旧只报状态。

## 5. 媒体模块

状态：已落地。它是**常驻型**的第一个也是目前唯一一个来源（见第 1 节那条界线）。

### 5.1 数据怎么拿到

MediaRemote 私有框架给的是歌名、歌手、专辑、时长、播放位置与取样时刻、播放速率、封面（JPEG，实测 600×600 约 26KB）、以及**发声那个 App 的 bundle ID**——最后这个是把它落到哪一格的唯一依据。

**macOS 15.4 起它只答复 Apple 签的平台二进制。** 实测 A/B：同一个调用，直接跑返回 0 个字段，装进 `/usr/bin/perl` 里跑返回 13 个。

**所以不需要任何第三方产物。** 桥就是我们自己的一个 dylib，由 perl 用 `DynaLoader` 装进它的进程，调用于是发生在 perl 的身份底下。社区方案（mediaremote-adapter）要编一个框架、再配一段 perl；我们只留下 `Bridge/nowplaying.m` 与 `Bridge/nowplaying.pl` 两个文件，由 `build-app.sh` 编进 bundle。

三条实测记下来，都是踩过才知道的：

- **社区对原理的说法不对。** 它说「bundle identifier 以 `com.apple.` 开头的进程被放行」，但 perl 进程里读到的 bundle identifier 是**空的**。起作用的是平台二进制身份，不是那个名字。
- **构造函数里不能直接干活。** dyld 还没加载完，从里面发 XPC 收不到回调（五秒无声）。甩到后台线程，等宿主进程自己起来。
- **stdout 接管道是全缓冲的。** 不逐行冲，条那边一行也收不到。

**桥的寿命就是管道的寿命。** 它读 stdin，条握着另一头；条一走它读到 EOF 随之退出。两端都不必去盯对方的 pid——与就地授权那条通道同一个形状（§4.7）。实测条退出后没有残留进程。

**进度在本地推算，不轮询。** 桥送来的是「某一刻的位置 + 速率 + 那一刻是什么时候」，剩下的自己往前推；真正要收推送的只有换歌、暂停这些实际发生的变化。

控制指令（play / pause / next / previous）每条起一个短命的 perl 进程。指令是稀疏的，为它维持一条常驻写通道不值得，而且那样还得自己处理指令与推送的交错。

**播放器开着但没加载曲目时照样注册成播放源**（实测：网易云刚启动就是这样，停着、字段全空）。那不是「在放东西」，格子上没有可说的，更不该为它亮一个均衡器——所以歌名与歌手都没有时当作没有播放源。

### 5.2 格子

```
  ┌───────────────────────────┐
  │  🎵         Bohemian…     │
  │     ▣       Queen         │
  └───────────────────────────┘
          ╰─ 图标右下角：封面，均衡器压在上面
             整格自下而上一层取自封面的颜色
```

- **第一行歌名，第二行歌手**，与会话那两行同位，不新发明版式。
- **图标右下角挂一枚封面，均衡器压在它上面。** 一枚记号答三件事：哪一格在发声、在放的是什么（换歌时封面交叉淡入）、在放还是停着（柱子跳不跳）。柱子取白色并压一层暗底——底下就是那张封面，同色的柱子在它自己身上认不出来。暂停时三根落到底、收成三个圆点：**没有声音就没有高度**。

  **柱子跟的是真的声音**，取自挂在发声那个进程上的 CoreAudio 进程 tap（见 §5.5）。这个尺寸上看不出任何频谱，能看出来的只有一件事——它跟不跟得上拍子，而那一点恰好就是「它是活的」。
- **整格取一层封面的颜色**，自下而上渐隐，与面板卡上那一层同一个手势。它与底色（`Backing`）共用同一个圆角和内缩，两套几何对不齐的话，格子一悬停就露馅。

三条与原方案不同，各有实测或推理支撑：

**歌名进文本层，宽度不是问题。** 曾经因为「切歌会让条抖」而想把歌名整个拿掉，那是错的：`BarLayout` 早就定了「有状态的格子文本区固定取上限宽度」，宽度只在上格子与退场时各变一次，**换歌根本不动宽度**。拿一个已经解决了的问题去砍掉这个功能唯一的正事，是让实现上的将就反过来改设计。

**封面做角标，并且与均衡器合成一枚。** 这一条推翻了先前的「封面不做角标」，理由是那条的论据是错的：它说四个角已经占满，而运行点根本不在图标上（见 §2）。右下角一直空着，浏览器那一格也一样空着。

改回来之后，先前那层颜色的毛病同时解掉了。**颜色需要一个看得见的出处**：它在面板上一直成立，因为封面就在旁边；格子上没有封面，同一层颜色便读作一块凭空的高亮。封面进了角标，颜色才有来处。

合成一枚而不是两枚，是因为这个角只放得下一枚：拆开是两个记号说一件半的事。

**声波动效换成均衡器，并且保留。** 原方案的声波与「条上不许有动效」冲突；细化那条规矩之后（见 §3）保留了下来。原先「声波 + 封面角标 + 歌名三样同时出现会不会过载」那个担心也不成立：声波与封面合成了一枚，本来就没有三样。

### 5.3 面板

```
╭────────────────────────────────────────╮
│ ♪  网易云音乐                          │
│ ┌────────┐                             │
│ │  封面  │  Bohemian Rhapsody          │
│ │        │  Queen                      │
│ └────────┘  A Night at the Opera       │
│ 1:24  ━━━━━━━✦────────────      −2:23  │
│         ⏮        ▶        ⏭            │
╰────────────────────────────────────────╯
```

- **标题行说的是哪个播放器，歌名归封面旁边。** 会话卡的标题行是「这件事叫什么」，照搬过来就成了歌名，而歌名在封面旁边还要再出现一次——同一行字在一张卡上出现两次。播放器的名字才是这张卡剩下的那个未答问题。
- **歌名、歌手、专辑靠着封面，从重到轻，整栏对着封面居中。** 专辑名与歌名或歌手重复时那一行不占位置：单曲的专辑常常就叫歌名，精选集常常就叫歌手名，它此时没有第三样东西可说。
- 整张卡取一层封面的颜色，随换歌一起过渡。
- 不画窗口缩略图——你打开这张卡是要控制播放，不是看那扇窗口长什么样。与会话卡同一条。
- 进度是**一根细线，时间贴在它两端**，不是一根粗条、也不是线下面压一行字。压在下面读起来像网页的图注，贴在两端才是播放器控件的样子。
- **已播那段带封面的颜色，并且从暗渐亮，末端最亮、收口干净。** 卡上唯一会动的元素本来是中性灰，而整张卡的底都取自封面——进度条正是该承接那个颜色的地方。

  **末端不画光晕。** 这条路试了三次都难看，失败的方式一次比一次清楚：实心圆加模糊（模糊盖不住实心核，成了一颗白点）、半径小而峰值高的径向渐变（落差太陡，边缘仍有形状，比不做还脏）、定长的白亮边（它固定 34pt，而进度只有百分之几时填充还不到那么长，整段就都被刷白）。**方向本来就是反的**：参考里那根线没有任何光晕，末端之所以像在发光，是因为填充自己从暗走到亮，收口反而干净。追加一层光去补，是在给一个做反了的渐变打补丁。
- **轨道不做凹陷。** 深色卡上未播那段必须比卡片更亮才看得见，凹陷只会得到一个黑洞；`.quaternary` 本来就随外观翻转。造出层次的是填充自己的明暗，不是凹槽。
- **线按帧走，不按秒走。** 每秒重算一次宽度的话，三分钟的歌铺在五百多点上，一秒近 3pt——那不是在走，是在跨步，末端有了光之后更成了光在瞬移。位置本来就是从时钟推的，按帧取样它自己就连续；也因此**不给宽度挂线性动画**，挂了的话跳转与暂停会滑过去，而它们该直接落位。两端的时间仍按秒重算。
- 播放键比左右两个大一圈。最常按的就是它，大一号手就不必瞄。
- **播放 / 暂停用字形形变**（`.contentTransition(.symbolEffect(.replace))`），不是两张图硬切。
- **不做拖动进度，末端也因此不放游标。** 一个圆点是在说「可以拖我」，而拖动要等常驻形态（§9）。点和拖动一起做。

**这张卡必须是预览卡的一档，不能另起一层浮层。** 从悬停普通窗口格滑到音乐格，应该是同一张卡在变形，不是两张卡对着淡——§3.1 那个亏已经吃过。而这正好把尺寸协议那道缝逼出来了：卡片的下半截由内容自报高度，会话与播放各写各的。**不需要拿「以后可能还有别的来源」去论证这道缝**，媒体一个就够了。

**点击语义不变**：左键还是召回窗口，控制键只在面板里。面板要收鼠标事件，因此复用了就地授权那一档的「指针从格子挪到卡片」的宽限——那是它第二个用户。

### 5.4 一格上撞了两种

会话压过播放。两者绑的是不同的 App，真撞上极少见；真撞上时该让位的是播放：它不会结束，等会话停了自然回来，而反过来会把一件正在等你的事盖住。

**一个 App 的窗口全关之后，它那一格上的状态照旧。** 窗口全关不等于事情结束——播放器关掉窗口在后台继续放歌是常态。那一格此时是占位槽（计划书 §6 M5），而占位槽这一支原先把状态写死成「没有」，于是关掉播放器的窗口，条上就什么都不说了。

占位槽因此**可以长出文本区**，宽度与窗口格同一条规则；没有状态时仍旧只有一个图标。代价是它与窗口格看起来一样，而点击语义并不同（一个召回窗口，一个激活 App）——这一条与「一个图标什么都不说」之间选了前者：说不出在放什么，才是这条产品线要解决的问题本身。

**悬停也照旧。** 格子说了，浮层这一侧却还只报一个 App 名——因为状态卡原先只从预览卡那一档长出来，而预览卡的前提是有一扇窗口可预览。没窗口的格子走的是名牌那一档，它于是成了唯一一处状态说不出口的地方，而按键正在那张卡上：窗口关掉之后反倒够不着播放控制。名牌因此也能带状态，缩略图那一半照常缺席（那一半本来就是「让位」，见 §5.2）。两处协议是共用的：

- **只有没窗口的格子这么做。** 有窗口的格子等停留过后长出预览卡，在名牌上先说一遍就成了「刚浮出来又换一副样子」。
- **长成卡片同样要先停留**，与预览卡同一个节奏。名牌是即时的，而一张三百点宽的卡在划过条时中途弹出来是另一回事。
- **标题仍旧是那个 App 的名字**，不换成会话的任务名。名牌先出、卡片后长，标题这一行在长的过程中始终是同一串字；换的话，那一行会在停留兑现的那一刻自己变一次。播放本来就报播放器的名字，两种状态因此在这一档上是同一条规则。
- **卡上有按钮时，指针离开格子要留一段宽限**，够它走过条与浮层之间那道缝——与预览卡上那条授权按钮同一个数。名牌那一档全靠「此刻悬停在哪一格」撑着，照常立刻收的话，那几个键永远点不到。

### 5.5 均衡器的电平

三根柱子跟的是真的声音。这一节记的主要是**四次失败的机理**——每一次都看着像调参问题，其实都是方案问题。

**取声。** `AudioHardwareCreateProcessTap`（CoreAudio 公开 API，头文件标 `API_AVAILABLE(macos(14.2))`）+ `initMonoMixdownOfProcesses:` + 一台私有聚合设备。聚合设备的子设备列表里必须挂上默认输出当时钟源——空列表也能把设备建起来，但那台设备不走 IO，实测一次回调都不来。

按**音频进程对象**挂，不按 Unix 进程。这一点正好解掉浏览器那个坎：Chrome、Arc 出声的是它们的 helper，而 helper 以自己的 bundle ID 出现在 `kAudioHardwarePropertyProcessObjectList` 里（实测 `company.thebrowser.browser.helper`），按前缀一匹配就找到了，不必碰进程树。匹配时**不按「此刻在不在出声」筛**：那个标志会翻而对象列表不会，按它筛的话扫描时刚好停着的播放器就永远挂不上。

**分频必须用 FFT。** 先前用一阶（6dB/倍频程）分频，「低段」到 2kHz 才衰减 20dB、「高段」到 200Hz 也只衰减 20dB——三段严重重叠，每一段都约等于总响度的一个副本。更糟的是**据此量出的数字会骗人**：那一版实测「每段每秒只摆动 3.5 到 10 分贝」，一度让人以为音乐的短时动态本来就小。换成 1024 点 FFT 真正分开之后，同样的音频、同样的量法，低段 30dB、中段 20dB、高段 18dB。

**按 hop 驱动，不按墙钟。** 每攒够 512 个样本分析一次（93.75 帧/秒，间隔严格均匀）。先前是每 1/30 秒去环形缓冲取一帧，相邻两次分析的实际重叠量是抖的；电平对此不敏感，而音头是**相邻帧的差分**，重叠一抖就直接变成音头噪声。

**驱动信号是音头，不是响度。** 响度是缓变量，拿它驱动只能得到起伏，得不到锁拍——「跟着 groove」在视觉上等于**音头同步**。用的是对数域半波整流的谱通量：每帧对每个格求 `max(0, dB[n] − dB[n−1])`，按段取平均。持续的贝斯长音帧间差分接近零，天然被忽略。

**映射不做绝对量程，做比值。** 对数差分已经免疫音量（整体音量只是给所有格加同一个偏移，帧间一减就消掉——实测印证：响度在 −35…−9 dBFS 之间跳，通量中位数始终 1.6–2.8），再除以自己的慢均值免疫曲风，最后过一条渐近饱和曲线免疫削顶。三层免疫叠起来，就不需要任何测量标定。

**这一处自适应与先前翻车的两版的分界在于跟踪的是均值而不是极值。** 那两版把量程的上端定义成自己最近的输出，状态一累积就自指，失效方式只有「死」和「爆表」两种，而且必然二选一。均值由输入主导、自然收敛；比值又让它只回答「此刻比平常高多少倍」，没有那个回路。均值的更新还必须**不对称**（往上打三折），否则音头自己会把均值抬上去，而比值该除的是非音头的基线。

**阈值与膝点都要逐段给。** 实测三段的比值动态差得很远：低段九五分位 1.86、顶 2.8，中段 1.50，高段只有 1.25；novelty 的动态范围因此差了近十倍。一刀切的话高段那根柱子会几乎全程为零——那正是「密集的内容会抬高自己的基线」这个特性走到极端。膝点的取法是让该段实测的顶级 novelty 映射到 0.8 上下。

**上屏走电平表的经典弹道：攻瞬时、保持、再回落。** 没有保持期的话峰顶会抽搐：一次音头持续两到四个分析帧，通量在峰附近晃，而 τ=0.13 秒在 94fps 的帧间只掉 8%，于是包络「落一点 → 被重触发 → 再落一点」，形成一个四十多赫兹的微颤。

**回落是读的时候按时间算的，不是写的时候算的。** 存下来的是「抬升那一刻的值 + 那一刻是什么时候」，与播放进度同一个手法。这样两次分析之间的每个显示帧都有自己的值。**视图这一侧一律不加隐式动画**——先前叠过三层低通（指数回落 + 30Hz 采样保持 + 70ms 缓出，而那段缓出每 33ms 就被重定目标、永远走不完），等效两百多毫秒，而 120BPM 的十六分音符才 125 毫秒。

**电平仍然留着，当背景。** 双层包络取较大值，电平层压到 0.35 —— 它负责在 pad、弦乐这种没有音头的段落里让柱子还有呼吸，不至于齐刷刷躺平。

最后一条与音频无关，但同样是这一路踩过的坑：`@Observable` **只跟踪 `body` 求值期间发生的读取**。把电平读在 `phaseAnimator` 的闭包里不算数，那个闭包是动画器存下来稍后调用的。症状是柱子只在换歌、暂停这些**别的**原因触发重画的那一刻动一下。

### 5.6 换歌的动效

先做的是交叉淡入，不对。**淡入淡出说的是「这个变成了那个」，不描述任何空间关系**——它是没有更好的东西可用时的兜底。而换歌是有关系的：你在队列里往前或往后走了一步，方向本身就是信息。

**真正的问题不是选哪一种过渡，是没有编排。** 那一行上曾同时跑着三套互不相干的机制（封面换 `id` 走 `transition`、三行字各走 `contentTransition`、结构分支插入删除），时长写成同一个数也不会插值成同一件事，读起来必然是「刷新了一下」。

- **同一条曲线、同一个时长、起点错开。** 封面领奏，两行字依次错开 45 毫秒跟上。错开不违反「一件事只能有一个速度」那条——那条针对的是**一个动一个不动**；错开是一件事在这一行上传过去，而且正是它显得贵的原因。
- **方向算在模型里，不在视图里。** 唯一可靠的信号是我们自己的上/下一首刚被按过（1.5 秒窗口），其余一律判向前——自动续播占绝大多数。判定挂在**歌的身份变了**这个条件上，不挂在指令上：播放器普遍是「位置超过三秒就从头开始」，按一下上一首多数时候根本不换歌。
- **封面绕竖轴翻过去**，方向写在旋转的正负号里；**文字只带一个方向性偏置**，不是位移——真横穿过去会读成跑马灯。
- **中途糊掉。** 这不是装饰：文字在交叠的那一刻是读不出来的，两串清晰的字叠在一起，眼睛会去读那个叠加态、读到乱码，整件事于是被读成「闪了一下」。糊掉之后它不再是字。
- **框架不动。** 进度条与三个控制键不参与，进度直接归零——那是另一首歌的时间轴，滑过去是撒谎。

三条实现上的坑，都记在这里：

1. **自定义过渡的修饰器必须实现 `Animatable`。** `.modifier(active:identity:)` 靠插值 `animatableData`，不声明就是 `EmptyAnimatableData`，两个状态之间瞬间切换——屏幕上什么都看不见。第一版的翻转就是这么消失的。
2. **动画事务要挂在稳定的父容器上，不能挂在换身份的那个视图上。** 后者自己就是被换掉的东西，换的那一刻它已经不在了，提供不了那次事务。这与 §5.5 末尾那条（`@Observable` 的读取不能放在动画器的闭包里）是同一类错：**把状态或事务托付给一个正在被替换的东西**。
3. **模糊不要碰硬裁剪**，边界上会切出一道生硬的线。文字那一栏的偏置距离取成了封面到文字的间距，退出的那一行走到头时正好贴着封面、而那时不透明度已经是 0，于是根本不需要裁剪。

## 7. 全局区

**降级为待定，第一版不做。**

原方案：Claude 限额（5 小时窗口 / 每周上限）是全局资源，不挂任何窗口 slot，放条右侧系统区，平时隐身，超阈值显示百分比。

不做的理由是它站不住：**支撑这个区存在的只有限额一件事，而限额在 Claude Code 自己的 statusline 里已经有了。** 一旦开始往里放第二样、第三样（VPN、电池、蓝牙设备电量都很自然），它就变成了 widget 栏——那是另一个产品，不是「窗口检索 + 注意力路由」这条线上的东西。

分界规则本身仍然成立、并且现在承担了另一个作用：**全局的归全局区**，而全局区不存在，所以不挂任何窗口的状态目前一律不做。这条挡掉的正是上面那串滑坡。

真觉得缺的时候再开，并且开的时候要先回答「除了限额还有哪一样值得」。

- **就地回答提问：做得到，已实测通过，但先不做。** 走的是 `PermissionRequest` 的 `updatedInput`：把原样的 `tool_input` 加上一个 `answers` 字段（问题原文 → 选中的 `label`）随放行一起递回去，会话不弹选择器、直接照这个答案走下去。线索来自工具自己的参数表——`AskUserQuestion` 有个 `answers` 参数，注为「User answers collected by the permission component」，而 hook 正跑在那个环节上。这条路比原先记的两条（拿否决当传声筒、往 pty 里敲键）都正当，它走的是这个事件本来就有的口子。`ExitPlanMode` 大概率同一形状，未验。

- **多会话落在同一格时，落选的那几条没有去处。** 现在只有排名最前的一条露面，其余的该在 hover 卡里排队，那一段没做。就地授权把这条从「少看见一点」变成了有代价的：同一格上两次授权同时挂着时，第二次要等第一次答完才露面（第一次一直在，所以不是哑的，但对面确实在阻塞着等）

- **右下角那枚角标在缩放下限处会不会糊。** 边长取图标的 0.38，条缩到 `iconFloor` 时约 14pt，柱子占掉正中 6pt 多，封面剩下的可见面积很小——有可能退化成「一块带柱子的彩色小方片」。退路是这个角只放均衡器，不放封面
- 整格那层颜色与底色的几档叠在一起是什么观感（尤其前台格的 `.focused`），只在一首歌上看过
- 均衡器的 tap 吃的是哪一份授权，没能查清。macOS 15 把那个面板改名叫「屏幕与系统音频录制」，所以**有可能**就是 Dockline 已经为窗口缩略图拿到的那一份，但同一个面板不等于同一份授权；也有可能进程 tap 根本不需要授权。两个测试环境（App 与终端）恰好都持有屏幕录制，分不开，而要分开就得去动用户的权限设置。对要做的事没影响——建不起 tap 或者收到的全是零，运行时自己会退回静默动画
- 取色改成了按色相分桶投票，纯黑白封面会落到「主色本来就是灰的」那一支，低饱和封面会得到一个淡色——两种都没有实机看过
- **一次逻辑上的变化会来好几条通知**，实测日志里见过 9 毫秒内「在放 → 停着」翻了一次：曲目信息与播放与否是分别问的，赶在中间取的那一次样就可能自相矛盾。均衡器收起要 0.22 秒，9 毫秒的翻转大概率根本没画出来，所以现在不去合并——**要先看见这个抖动，再决定合不合并**，凭推测加一个防抖窗口正是这份文档一路在避免的东西
- **多个播放源同时在放**时 MediaRemote 只报一个「正在播放」。够用，但用户预期未必如此——他可能想知道另一个标签页也在出声
- 阈值与默认值（done 未读超时时长）待实际使用调参

## 9. 常驻形态与全屏浮出（只有设计，未实现）

两件事共一个底：**面板现在只有悬停一种活法**——指针一走就收，因而它答得了「看一眼」，答不了「留着它」和「条根本不在的时候怎么办」。

### 9.1 常驻形态

面板要能钉住，对会话与播放都成立。播放尤其需要：现在要按下一首就得先把指针停到那一格上等它浮出来。

**怎么钉：面板上给一个图钉。** 不用点格子（那是召回窗口，不能动）、不用新手势、也不用修饰键——你要钉它的时候本来就正看着它，按钮就在眼前。再点一次取消，Esc 也取消，状态自己结束时（会话退场、播放停止）自动撤下。

**同时只钉一个。** 条上方就那么点地方，钉第二个时第一个让位。

三处要连着改，都不是小改动：

- **收事件。** 钉住之后指针不在上面也得收键鼠，`allowsHitTesting` 那一档要跟着钉住走，不再只看「卡上有没有按钮」。
- **面板的高度。** `BarPanel` 平时只留玻璃条那么高，浮层要用时才长出来——那是为了不让截屏工具一直看见一个半屏大的窗口候选。钉住会把这个代价长期化，所以钉住时要按那张卡的实际尺寸精确长高，不能沿用「浮层那一档」的固定值。
- **让位。** 大预览（按住空格）占的是同一块地方，钉住的面板那几秒要让开。

**待答**：条自动隐藏或进了全屏时，钉住的面板跟着藏，还是留下？留下的话它就变成了 9.2 那个东西，两者要合成一条路，不该各写一套。

### 9.2 全屏时单格浮出

全屏写代码，agent 在等授权，而条整条藏着——这正是「尽可能不用切窗口」失效得最彻底的场合。

**做法是让那一格自己带着面板浮出来，不是把整条 bar 唤回来。** 这个差别是要紧的：唤回整条是在说「回来看看条上都有什么」，浮出一格是在说「这一件事在等你」。后者才是注意力路由该有的动作，前者是打扰。

**只有「在等你」那一档配浮出来。**

- 在跑的不浮 —— 任务运行期间不打扰，这是第 1 节的本职。
- 终态不浮 —— 它是未读的，会一直等到你出全屏，不急在这一刻。
- 等待里也分：**待授权、待回答**这种能就地办掉的才浮；待输入那种只是通知，不值得穿透全屏。

技术上成立：面板本来就是 `.fullScreenAuxiliary` 加高 level，能浮在原生全屏之上（§4 已验）。

**待答，三条都不小**：

1. **浮在哪儿。** 条藏着，那一格的横坐标对用户没有意义了。屏幕底部居中？还是像通知一样右上？前者延续「条在下面」的肌肉记忆，后者是系统里既有的「有事找你」的位置。
2. **怎么收。** 答完就收是清楚的；没答但用户不想理它呢——点别处收、还是一直挂着？挂着就成了全屏里的一块顽固浮层，而收掉就等于替用户忽略了一件他没处理的事。
3. **与 9.1 的钉住合流。** 两者都是「不靠悬停活着的面板」。分开写会有两套生命周期，撞在一起（钉着一个，全屏里又浮出另一个）没人知道该听谁的。
